open-tick · v0.1 · extraction done

The beat a simulated machine keeps.

open-tick is the part of a simulated machine that does not depend on the machine: one clock that never reads the wall, scenarios as data, traces, and the bridges that carry signals to your microcontroller. Applications bring the physics; open-crank, a heavy-duty diesel, already runs on it.

// why

To a microcontroller, the world is signals.

Voltages on pins, edges with timing, frames on a bus. Your firmware cannot see the crane, the robot or the train behind them. If something produces those signals faithfully enough, it cannot tell a simulated machine from a real one.

Writing the first machine, a diesel engine, meant writing a clock, scenarios, traces and a CAN bridge, and none of them cared about diesel. open-tick is that part, so the next machine does not have to write it again.

"One clock, one step, any machine, and an exact statement of how faithful it is."The promise open-tick is built to keep. The last part is planned.

// what runs today · v0.1

The runtime of a machine, without the machine.

Version 0.1 is the extraction: the parts of open-crank that did not depend on a diesel engine, as a library with its own tests. Every claim below points at the code that backs it.

One clock that never reads the wall

Simulated time is a 64-bit count of nanoseconds that whoever runs the machine advances. A driver only decides how fast: as fast as the CPU can, or paced by the wall clock, measuring how late it wakes.

timebase.h · driver.h

Scenarios are data

Each application registers its signal names; scenarios are plain CSV played at the start of each step. A typo fails loudly with its line number instead of running a different test.

scenario.h · player.h

CAN and CAN FD bridges

Frames up to 64 bytes, in memory for tests and CI, or on Linux SocketCAN for a vcan bus or a USB-CAN adapter. CI round-trips classic and FD frames on vcan.

can.h · socketcan.h

Traces that refuse to shift

Applications declare their columns once. A value of the wrong kind, a missing column or text that would break the CSV is reported, instead of plotting the wrong signal under the right heading.

trace.h

A core that builds anywhere

The core is ISO C11 and its standard library only: no OS headers, no clocks, no sockets. CI checks the rule and builds the core on macOS, where the Linux host zone is left out.

tools/check_deps.sh

Tests that can fail

Sanitizers, gcc and clang, and 18 deliberate mutations: CI breaks each behaviour applications rely on and requires the tests to notice.

// how it works

Applications bring the machine. open-tick brings the beat.

An application registers its signals and trace columns and steps its plants; open-tick plays the scenario, keeps the time and carries the frames. The device under test never knows which side of a bridge it is on.

the same loop for every driver
OtkDriver d;
otk_driver_init(&d, kind, otk_ns_from_ms(10));   // free-run in CI, paced for SIL
while (!otk_player_done(&player, now)) {
    otk_player_advance(&player, now);            // scenario events due at this step
    machine_step(&m, &to_dut);                   // your physics; frames out
    dut_step(&dut, &to_machine);                 // in memory, or across a bridge
    otk_driver_wait(&d);                         // returns at once, or sleeps
}

Message transports CAN today

The device under test sends when it wants and the machine answers in its next step. Tolerances in milliseconds, so the host can carry them: no special hardware.

  • CAN and CAN FD, in memory or on SocketCAN (v0.1)
  • UART for simple machines, from open-robots (when open-robots starts)
  • open-tick carries the bytes; the application decides what they mean

Signal-level transports planned

Edges, levels and registers, answered within a bit time. They live in the bridge, which the core feeds once per step.

  • rotary patterns: encoders and 60−2 crank wheels are one primitive
  • pulse capture: PWM duty, direction, injector timing
  • I²C and SPI slaves answered from a register map

The fidelity contract planned · v0.4

"The microcontroller cannot tell the difference" is true only within limits. Each machine will declare what it needs from a bridge, and each bridge what it guarantees. A run that cannot be faithful is refused, naming the signal and the number that fails, instead of passing against a degraded reality.

During runs on real silicon, the measured jitter and latency go into the trace, so the claim is checked rather than assumed.

From clone to a flywheel in a minute.

Any host with a C11 compiler and CMake builds the core; the drivers and the SocketCAN bridge need Linux.

  • Run the tests, including the determinism check.
  • Run the flywheel free, or paced by the wall clock.
  • Use it from your own application with add_subdirectory or a submodule, as open-crank does.
shell
$ git clone https://github.com/Open-Heavy-Machinery/open-tick.git
$ cd open-tick
$ cmake -S . -B build && cmake --build build
$ ctest --test-dir build --output-on-failure
# the same run, free or in wall-clock time
$ ./build/otk-flywheel examples/flywheel/step.csv
$ ./build/otk-flywheel examples/flywheel/step.csv --driver paced

From a bus to the pins, one finishable step at a time.

No dates. Each milestone is driven by a machine that needs it, and the full plan with exit criteria is in ROADMAP.md.

  1. v0.1Extraction: open-crank runs on open-tickdone

    Timebase, scenarios and player, CAN queues, trace writer, pacer, drivers and the SocketCAN bridge, with open-crank consuming them as a git submodule.

    • open-crank's tests and 18 mutations pass on open-tick
    • all six traces byte-identical, checked in CI
    • the vcan demo runs as two processes in CI
  2. v0.2Oracle: grading by what the transports showpass / fail

    Grade any device under test only by what is observable on its transports, with reaction times measured from the injected event and invariants checked over the whole scenario. Pulled by open-crank v0.2.1: proven there first, in its acceptance suite over the bus, then moved here as the runtime was. Exit: open-crank's verdicts are identical before and after the move, and otk-flywheel is graded by it too.

  3. v0.3Transport faultsfault injection

    Lost, corrupted and delayed frames, bus-off and jitter, for every application; domain faults stay in the application. Pulled by open-crank v0.3. Exit: open-crank's fault scenarios run on them, each fault has a mutation check, and otk-flywheel uses at least one.

  4. v0.4Tang Nano 20K bridgeFPGA · pins

    The first signal-level bridge: crank and cam wheels as rotary patterns, injector capture and analog outputs, the bridge as the clock, the host-to-bridge protocol and the first fidelity contract. Pulled by open-crank v0.4. Exit: open-crank's Level 2, an engine-ECU firmware that synchronises on the crank and holds speed, within a measured jitter and latency budget.

  5. v0.5ProfilesYAML → C

    Machines described in reviewable files, compiled to C: parameters, wiring and provenance, never equations. Pulled by open-crank v0.5. Exit: open-crank's two-engine machine and its engine as profiles, with identical traces.

Track RRenode virtual-time driverparallel

Step the simulation in lockstep with an emulated microcontroller, so real firmware runs in the loop in CI without a board. Pulled by open-crank's Track R.

When a sibling startslater

These keep their scope and exit criteria, and get a version number when open-robots, or another sibling application, actually starts. Until then nothing here is built.

  • open-robots in SIL. One DC motor with an encoder, over a UART link through the host's serial port, and a written list of what the second machine forced to change.
  • Raspberry Pi Pico bridge. Quadrature outputs and PWM capture on real pins. Exit: a microcontroller closes a speed loop on four simulated motors from encoder edges, and moving between the Pico and the Tang Nano 20K changes only configuration.
  • Register-mapped slaves. I²C and SPI devices answered by the bridge from a register map the core updates each step. First device: an IMU for open-robots.
// scope

Honest about what it is.

It is

  • The runtime of a simulated machine: time, scenarios, traces and bridges.
  • Deterministic where it can be: free-running runs are identical, byte for byte.
  • Measured where it cannot be: paced runs report how late they woke up.
  • A core for any machine, grown only when a second machine needs it.

It is not

  • A physics engine or a modelling language. Physics lives in applications.
  • On the device under test. Your firmware never links open-tick.
  • An MCU emulator, or a protocol stack for your firmware.
  • Power HIL, or certified. Logic-level signals only, never real machinery.
Open Heavy Machinery · open-tick · Apache-2.0 github.com/Open-Heavy-Machinery

Tools for practice, development and regression testing: not certified, and never to be connected to real machinery. Bridges carry logic-level signals only and never drive motors, actuators or anything that carries power.
