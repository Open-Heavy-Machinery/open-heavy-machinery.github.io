open-crank · v0.2 · reference board on the bus

A heavy-duty diesel that answers back.

Connect your own firmware over J1939 and practise against an engine you could never keep at home. open-crank simulates the engine, its ECU and its hydraulic load: develop, test and break your controller on a laptop, in CI and on a cheap STM32G431 board today. No engine required.

// why

The barrier is access, not knowledge.

Real engines, dynamometer cells and HIL rigs are expensive and booked solid. Most engineers who want to learn energy- and power-management control never get past a bench-supply motor, and teams arrive at the test bench with code that has never felt a real load.

Open Heavy Machinery builds the missing half of the loop in the open: plants, engine-side peers and test infrastructure you can read, run in CI, and argue with.

"A control regression should fail a build, not a shift."The promise every open-crank test is written to keep.

// what runs today · v0.1

A complete control loop, on the bus, in CI.

Version 0.1 is a Level 1 vertical slice: a machine controller asks a simulated engine for speed over J1939 while a hydraulic hoist loads it, and tests prove what happens. Every claim below points at the code that backs it.

A plant that never cheats

Mean-value model of a 10.5 L inline six of the D936L A6 class: brake-torque map, friction, turbo lag, starter. Physics only: it never starts itself and never quietly helps the controller.

sim/core · sim/plants/d936la6

An engine ECU with opinions

A simulated engine ECU sits between your controller and the physics: starter control, idle and speed governor, governed ceiling, stale-command timeout, overspeed trip latched until the engine stops.

sim/engine_ecu

J1939 as the standard means it

TSC1 in; EEC1, ET1 and EFL/P1 out. A saturating codec that handles "not available", and an engine that reports who is in control, so your controller can tell when it is not.

docs/bus-interface.md

A controller that goes to firmware

The reference machine controller is plain C that depends on three standard headers. CI builds it for a Cortex-M4F on every push: about 2.6 KB, no double, nothing from libc.

portable/

Scenarios are data

Start, hoist, lose the bus, overspeed: plain CSV files, shared by the tests, the headless runner and the SIL. A typo in a signal name fails loudly instead of running a different test.

scenarios/

Tests that can fail

Closed-loop tests for every exit scenario, sanitizers, and 18 deliberate mutations: CI breaks each safety behaviour on purpose and requires the suite to notice. Every pull request's traces are compared, byte for byte, with its base.

// how it works

Your controller sees a bus. Behind it, a whole machine.

In Level 1 the device under test only touches CAN, exactly like a crane or vessel controller does. That is what lets the same firmware run against a laptop and against a real board.

Level 1 · machine controller now

Your firmware is the machine's supervisory controller, a crane, vessel or generator-set controller, EMS or PMS. It asks the engine for speed, reads its status and drives the loads. All it needs is a CAN bus; vcan will do.

Level 2 · engine ECU v0.4

Your firmware is the controller inside the engine. It reads crank and cam signals and sensors and commands fuel, so it needs microsecond-accurate waveforms: they will come from open-tick's Tang Nano 20K bridge.

portable/

The controller and the J1939 codec. Depends on stdint.h, stdbool.h, stddef.h and nothing else. Goes to firmware.

sim/

Plant physics, the engine ECU, loads, the bench, scenarios. Host only, double precision, never reads a clock.

platforms/

Thin glue per target: headless host, Linux SocketCAN and the STM32G4 reference board today; then FPGA; Renode in parallel.

external/open-tick

open-tick, pinned as a git submodule: the clock, scenarios, traces, the pacer and the SocketCAN bridge. open-crank brings the engine.

Dependencies point one way, and CI enforces it: if portable/ ever picks up a printf, a socket, a software-emulated double or anything from open-tick, the build fails.

// run it

From clone to closed loop in a minute.

Any machine with a C11 compiler and CMake. No CAN hardware, no root, no engine.

  • Run every scenario headless and get a CSV trace.
  • Put the simulated machine on a vcan bus and watch it with candump.
  • Bring your own controller: the bus contract fits on one page.
shell
$ git clone --recursive https://github.com/Open-Heavy-Machinery/open-crank.git
$ cd open-crank
$ cmake -S . -B build && cmake --build build
$ ctest --test-dir build --output-on-failure
# a 25 s hoist scenario, closed loop, in milliseconds
$ ./build/open-crank-run scenarios/hoist_step.csv --trace hoist.csv
// direction

From a laptop to an FPGA rig, one finishable step at a time.

No dates. A milestone is done when its exit criteria are met, and each one is small enough to finish and useful on its own. The full plan, with criteria, is in ROADMAP.md.

  1. v0.1Level 1 vertical slice, in CIdone

    Plant, simulated engine ECU, J1939 codec, portable controller, scenarios, closed-loop tests and the Cortex-M4F portability check.

    • closed-loop scenarios, portability, mutation checks, parameter provenance
    • first CI run on GitHub
    • the vcan demo verified end to end, now in CI
    • runs on open-tick, with all six traces byte-identical (#1)
  2. v0.1.xMISRA-oriented checks and stack usage in CIdone

    The free cppcheck MISRA addon over portable/, findings by rule number only, each one fixed or documented as a deviation; and the stack usage of every function in the Cortex-M4F build. MISRA-oriented, because the addon covers only part of the rules: passing it does not imply compliance.

  3. v0.2Reference board on the busdone

    A cheap reference board, an STM32G431 with a CAN transceiver and a SocketCAN USB-CAN adapter, with a bill of materials and a bring-up guide from scratch, running the portable controller unchanged. Latency measured first, tolerances written down before comparing, then the hoist scenario against the wall-clock SIL; the worst observed execution time (measured with the DWT cycle counter; not a proven bound) and stack of the controller step on the board. Real silicon, never real machinery.

    • hoist scenario with the board in the loop within tolerances written beforehand, three runs, checked with tools/compare_runs.py (results)
    • bring-up guide followed from scratch on a clean clone (BRINGUP.md)
    • controller step: worst observed 13.5 µs on the board; worst-case stack 68 bytes, checked in CI
    • released as v0.2, with the traces attached
  4. v0.2.1Acceptance suite over the busany controller

    A runner that grades any device under test by its CAN frames alone, with a pass/fail report per scenario. Criteria use only what is observable on the bus, timed from the injected event: within T ms of losing EEC1, TSC1 is sent with override disabled and OC_PUMP_CMD displacement is 0; no TSC1 ever requests more than high idle. The reference controller must pass; a deliberately broken one must fail.

  5. v0.3Robustness on the boardfault injection

    Lost, late and corrupted frames, bus-off, DM1, and a watchdog with a defined state after reset. Numbered safety requirements, each traced to a test, and a written safe state. Optionally, a black box and configuration in EEPROM.

  6. v0.4Level 2: your firmware as the engine ECUTang Nano 20K · open-tick

    The simulated ECU steps aside and fuel comes from your injector pulses. 60-2 crank and cam waveforms, analog sensors and injector capture from open-tick's Tang Nano 20K bridge, with a stated and measured jitter budget. An FPGA, because Level 2 needs many independent timed channels at once. The plant stays on a CPU.

  7. v0.5Two engines on one machineJ1939-81

    Two engines on one bench with distinct source addresses, J1939 address claiming and its conflicts. A fault on one must not disturb the other. The bench is generalised, not the plant.

  8. v0.6Marine 2-stroke plantpropeller load

    A Mitsui MAN B&W 9S50ME-class engine (9 cylinders, 500 mm bore), driving a propeller through its own ME-style control interface. The plant interface is extracted from what both engines really share, not guessed before.

  9. v0.7Electrical plant and power managementPMS

    Generator sets on the multi-engine bench, an electrical bus, load sharing and breakers, and a blackout-and-recovery scenario for power-management development.

Track RFirmware in the loop in Renodeparallel · after v0.2

The board's firmware in an emulator, headless in CI, checked against the board's own trace. The virtual-time driver is open-tick's; open-crank keeps the board's side: for the G4, a platform description of our own on Renode's STM32 FDCAN model, assumed but not yet verified to match, with an STM32H7 as fallback. For anyone without a board, the free path is the SIL.

Beyond 1.0, with no dates: 3D machines in separate repositories, such as a generic crane in Gazebo or O3DE with ROS 2, where every signal has exactly one owner, simulated or real.

Later, unscheduled: aftertreatment, FMI/FMU export, a trace dashboard, Python bindings.

// engineering principles

Built to be trusted, so it is built to be checked.

Each principle is enforced by something that can fail: a test, a CI job, or a documented rule.

01

The plant answers honestly

Physics in the plant, decisions in a separate engine ECU. If the engine stays alive, it is because your controller and the ECU kept it alive.

02

Same source, laptop to board

The controller zone builds for a Cortex-M4F on every push. A stray printf or double fails the build.

03

The real protocol

TSC1 means what SAE J1939 says. The two project-specific messages are named OC_* and documented as not J1939.

04

Tests that can fail

CI breaks each safety behaviour on purpose and requires the tests to catch it. A test that cannot fail proves nothing.

05

Every number has a source

Each parameter is marked as sourced, estimated or inherited and awaiting a citation. Representative, never presented as calibrated.

06

Generality is earned

A crane diesel and a large marine two-stroke must share one runtime before any plant interface is frozen. The runtime itself moved to open-tick only once every trace stayed byte-identical.

// scope

Honest about what it is.

It is

  • A plant that answers back, representative of its engine class.
  • A realistic engine-side peer on a real protocol.
  • A way to arrive at the bench with working code and a shorter list of things to try.
  • Open and auditable: Apache-2.0, original protocol code, cited parameters.
  • Bring your own firmware: any board, RTOS or language that speaks CAN.
  • A place to practise critical-firmware techniques (not a certified tool): MISRA-oriented and stack checks in CI since v0.1.x, and the worst observed execution time on the board since v0.2; acceptance tests over the bus are planned for v0.2.1.

It is not

  • A certified tool. No ISO 26262 or IEC 61508 argument; never for signing off a calibration.
  • A digital twin. Mean-value models, not crank-angle resolved combustion.
  • A replacement for a test bench, or a full J1939 stack.
  • Connected to real machinery. Ever.
// get involved

Pre-alpha, and the right moment to shape it.

A well-argued issue is worth more than a pull request right now. Three contributions matter most:

Source a parameter

Bench access to either reference engine class? Correct a number in parameters.md and cite where it comes from.

Check a layout

Own a copy of SAE J1939-71? Compare it with the bus interface and report any byte that disagrees.

Bring a controller

Point your own machine controller at the simulated engine through the bus contract, and open an issue with what broke, in either one. An acceptance suite that grades any controller by its frames is planned for v0.2.1.
